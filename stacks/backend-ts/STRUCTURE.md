# Project Structure & Conventions

The canonical layout every new backend-ts service produces. It inherits the
stack-agnostic rules in [`../../CORE.md`](../../CORE.md) — this file adds the
Hono-on-Cloudflare-Workers specifics and never relaxes a CORE rule. Designed for
**thin routes, testable services, and easy LLM traversal**: predictable folder
names, a README in every source directory, no barrel files (every import points
at the file that holds the thing).

## The runtime shapes everything below

This service runs on **workerd**, not Node and not Bun. That is not a deploy
detail — it changes the code:

| Node/Bun habit | On Workers |
| --- | --- |
| `process.env.X` | A **binding** — `c.env.X`, or `env` from `cloudflare:workers` |
| `Bun.serve(...)` / `app.listen()` | `export default app` — the runtime calls it |
| A module-level connection pool | Per-request connections; an isolate is shared |
| `fs`, native modules | Not available. `fetch`-based clients only |
| A long-running background job | A queue, a cron trigger, or `ctx.waitUntil` |

When a library's README says "Node.js", verify it runs on workerd before adding
it. `LIBRARIES.md` names the ones that do.

## Folder tree

```
<app>/
├── src/
│   ├── app.ts            # The Hono app — the oRPC handler + plain routes (wiring only)
│   ├── index.ts          # Worker entry — `export default app`. The ONE default export
│   ├── rpc/              # The typed API surface — oRPC procedures. README.md
│   │   ├── base.ts       #   the shared builder: context type + shared middleware
│   │   ├── router.ts     #   the composed router — this file IS the API's shape
│   │   ├── <domain>-procedures.ts
│   │   └── __tests__/
│   ├── routes/           # Plain HTTP: /health, webhooks, auth callbacks. README.md
│   │   └── __tests__/    #   route tests via exports.default.fetch(...)
│   ├── services/         # Business logic — framework-agnostic, unit-testable. README.md
│   │   └── __tests__/
│   ├── utilities/        # Shared pure helpers (dates, formatters, …). README.md
│   ├── constants/        # env.ts (Zod-validated bindings), enums. README.md
│   └── types/            # Cross-cutting TS types. README.md
├── scripts/              # guardrails/run.sh — folder-tree gate (part of `bun run check`)
├── wrangler.jsonc        # Worker config: name, entry, compat flags, vars, environments
├── worker-configuration.d.ts  # GENERATED by `wrangler types`. Committed; never hand-edited
├── vitest.config.ts      # Vitest through @cloudflare/vitest-pool-workers (runs in workerd)
├── tsconfig.json         # strict + path alias
├── .oxlintrc.json · .oxfmtrc.json · lefthook.yml
├── .dev.vars.example     # local SECRETS template (.dev.vars itself is git-ignored)
├── .github/workflows/    # ci.yml (the gate) + code-review.yml (AI review)
├── CLAUDE.md             # agent rules + repo map (read first)
└── README.md             # human + agent entry point
```

> Folder vocabulary (`rpc`, `routes`, `services`, `utilities`, `constants`,
> `types`) is intentional. Middleware is added under `src/middleware/` **only
> when** an integration is wired — add the new dir to `src.topLevel` in
> `guardrails.config.json` when you do (see `SETUP.md`).
>
> **`src/db/` is not on that list by default.** With Drizzle, the database is
> its own workspace package — see [`../database-ts/`](../database-ts/STRUCTURE.md)
> — and this service imports from `@<project>/database/…` instead. A bare Turso
> client (SETUP Phase 6a, no ORM) may still live in `src/db/`; if you later take
> the package, that directory goes away.

## `rpc/` vs `routes/`

Both serve HTTP; they are not interchangeable.

- **`src/rpc/`** is the product API — everything our own console and mobile app
  call. Procedures declare Zod input **and** output schemas, oRPC validates both,
  and the clients are typed from those same declarations. Served under `/rpc`.
- **`src/routes/`** is for HTTP that cannot be a procedure: `/health`, webhooks
  from third parties (they choose the shape), OAuth callbacks, anything a
  non-TypeScript caller hits.

If one of our own clients calls it, it belongs in `rpc/`. New endpoints default
there; a plain route needs a reason.

## Path alias

Configured in `tsconfig.json` and resolved by the Workers bundler. Always import
via the alias — never deep relative paths like `../../services/health`.

```ts
@/*   → src/*
```

So `@/app`, `@/constants/env`, `@/routes/health-route`, and
`@/services/health-service` all resolve from anywhere in the tree.

## App assembly & serving

Two files, one job each — keep them separate:

- **`src/app.ts`** builds and exports the Hono `app`, typed as
  `new Hono<{ Bindings: Env }>()` so every binding is checked at the call site.
  Every route module and every middleware is mounted here. This file is **wiring
  only** — no business logic.
- **`src/index.ts`** is the Worker entry: `export default app`, and nothing else.
  A Hono app already has a `fetch` method, so it *is* a valid Worker handler; the
  runtime calls it. This is the **only default export in the codebase**, and the
  lint config turns `import/no-default-export` off for this file alone.

```ts
// src/index.ts
import { app } from '@/app';

export default app;
```

## Config: bindings, vars, and secrets

`Env` comes from `worker-configuration.d.ts`, which `wrangler types`
(`bun run cf-typegen`) generates from `wrangler.jsonc`. It is generated **and
committed** — `tsc --noEmit` needs it on a fresh clone — and CI fails if it has
drifted from the config.

The split between the two config homes is a security boundary:

| Kind | Lives in | Visible in review | Example |
| --- | --- | --- | --- |
| Non-secret config | `vars` in `wrangler.jsonc` | yes (committed) | `APP_ENV` |
| Secrets | `.dev.vars` local, `wrangler secret put` deployed | no | `TURSO_AUTH_TOKEN` |

`src/constants/env.ts` parses them with a Zod schema and exposes **accessor
functions** rather than module-level constants: a Worker module is evaluated once per
isolate, before any request, so reading config eagerly there couples startup to
values a test may want to override. Every environment needs its own secrets —
`wrangler secret put X --env staging` is a separate act from the production one.

## Hard conventions

These inherit CORE. Most are **machine-enforced** by `bun run check` — via
`.oxlintrc.json` (oxlint), `scripts/guardrails/run.sh` (folder tree), and Lefthook
pre-commit — so the gate fails on a violation rather than a reviewer catching it.
Each rule below names its enforcer; `(review)` means it's a convention a human/agent
upholds, not yet a machine check. See
[`templates/CLAUDE.md.template`](./templates/CLAUDE.md.template) for the full
blocked-patterns list.

1. **No barrel files.** Never an `index.ts` that only re-exports. Import the
   concrete file: `import { getHealth } from '@/services/health-service'`. —
   enforced by `no-restricted-imports` (barrel imports) + `guardrails`
   (no `index.ts` under `src/` except the `src/index.ts` entry).
2. **No deep relative imports.** Use the `@/` alias, never `../../x`. — enforced
   by `no-restricted-imports` (`../../*` pattern).
3. **Thin routes.** A module under `src/routes/` parses the request, calls a
   service, and shapes the response — no business logic, no direct DB access. —
   (review).
4. **Services hold logic.** Put the real work in `src/services/` as
   framework-agnostic functions, so they unit-test without the HTTP layer. —
   (review).
5. **One route module per resource.** `src/routes/user-route.ts` owns `/users`;
   mount it in `src/app.ts`. — (review).
6. **Allowed `src/` layout.** Only `rpc routes services utilities constants types`
   as top-level dirs (each with a `README.md`), plus `app.ts` + `index.ts` at the
   root. — enforced by `guardrails`.
7. **Filename ↔ content.** Kebab-case filenames named after the export
   (`health-service.ts` → `getHealth`). One primary export per file. — enforced by
   `unicorn/filename-case` (kebab-case); one-export-per-file is (review).
8. **Named exports only, except the Worker entry.** `src/index.ts` must default-
   export the app because the runtime requires it; everywhere else is named, so
   every symbol is grep-able. — enforced by `import/no-default-export`, off for
   `src/index.ts` and config files only.
9. **Config through bindings, never `process.env`.** Read it via
   `src/constants/env.ts`, which parses the bindings with a Zod schema; add a var
   by declaring it in `wrangler.jsonc` (or `.dev.vars` for a secret),
   regenerating types, and adding it to a schema there. — enforced by
   `cf-typegen` drift check in CI + (review).
10. **Zod at every boundary, types inferred from it.** Config, procedure inputs
    and outputs, webhook payloads, anything parsed. `type X = z.infer<typeof X>`
    — never an interface declared beside a schema (CORE rule 13). — enforced by
    `no-restricted-imports` (competing validation libraries) + review.
11. **Nothing unused, nothing duplicated.** `knip` fails the gate on an unused
    file, export, or dependency; `jscpd` fails it on copy-paste. — enforced by
    `knip.json` and `.jscpd.json` (`threshold: 0` is what fails the gate;
    `exitCode: 1` covers the case where the threshold is later raised).
12. **Secrets never enter `wrangler.jsonc`,** and `.dev.vars` is never committed.
    — enforced by `guardrails` (fails if git tracks `.dev.vars`).
13. **Co-locate tests** in a sibling `__tests__/`: `health-service.ts` →
    `__tests__/health-service.test.ts`. Keep the test tree flat. — enforced by
    `guardrails` (fails on centralized test dirs and any `*.test.*` under
    `src/` outside a `__tests__/`).
14. **Tests run in the real runtime, against real data.** The Vitest pool boots
    workerd with this project's `wrangler.jsonc` and `.dev.vars`, so a test hits
    a real Turso database. A mock-only test is banned (CORE rule 7) — it proves
    the mock works and hides every integration break. — enforced by
    `vitest.config.ts` (the pool) + (review) for the mock rule.
15. **No `any`.** No `as any`, `: any`, `as unknown as T`. Use `unknown` + type
    guards. — enforced by `typescript/no-explicit-any` + the `no-unsafe-*` family.
16. **No `console.log` / `debugger`.** Use `console.warn` / `console.error` (both
    reach Workers Logs) or the structured logger, if wired. — enforced by
    `no-console` (warn/error only) + `no-debugger`.
17. **`max-lines: 300`** per file, code lines only (blanks/comments skipped; tests
    exempt). — enforced by `max-lines`.

## Procedures

A procedure declares what goes in and what comes out, and oRPC validates both —
the input before the handler runs, the output before it leaves. The clients'
types are derived from the same schemas, so the contract cannot drift from the
implementation.

```ts
// src/rpc/shift-procedures.ts
import * as z from 'zod';
import { base } from '@/rpc/base';
import { listShiftsForLocation } from '@/services/shift-service';

const Shift = z.object({ id: z.string(), startsAt: z.iso.datetime() });

export const list = base
  .input(z.object({ locationId: z.string() }))
  .output(z.array(Shift))
  .handler(({ input, context }) => listShiftsForLocation(context.env, input.locationId));

export const shiftProcedures = { list };
```

Rules that hold for every procedure:

1. **Build from `base`, never from a bare `os`.** `base` is where the context
   type and the shared middleware live; a procedure built from `os` compiles
   and then has an untyped context.
2. **Declare `.output(...)`, not just `.input(...)`.** Without it the response
   is whatever the handler happened to return, and the client's type is a guess.
   The output schema is what makes the contract two-way.
3. **Handlers stay thin.** Parse, call a service, shape the result — the same
   rule as a route. The work lives in `src/services/`.
4. **`src/rpc/router.ts` is not a barrel.** It composes a value whose shape *is*
   the API, and reading it should tell you the whole surface. Adding a domain is
   one line there.

## Sharing the API type

Clients are typed against the router, which means the type has to travel:

| Layout | How | Notes |
| --- | --- | --- |
| **Monorepo** (API + console in one repo) | The client does `import type { AppRouter } from '@acme/api'` | Type-only, erased at build — no server code reaches the client bundle. Simplest; use it if the repos can live together. |
| **Separate repos** (this kit's default) | Publish a small **contract** package (`@orpc/contract` + the shared Zod schemas) that both sides depend on | The API implements the contract; clients are typed as `ContractRouterClient<typeof contract>`. Versioning the contract is what makes a breaking change visible instead of a 3am surprise. |

Pick one deliberately and write the choice into `CLAUDE.md`. What does **not**
work is hand-copying types into the client: they drift the first time someone is
in a hurry, and nothing tells you.

## Testing

`vitest.config.ts` runs every test inside workerd through
`@cloudflare/vitest-pool-workers`, reading the same `wrangler.jsonc` the deploy
uses. Drive the service through its real entry point:

```ts
import { exports } from 'cloudflare:workers';
import { describe, expect, test } from 'vitest';

describe('GET /health', () => {
  test('returns ok', async () => {
    const response = await exports.default.fetch('http://localhost/health');

    expect(response.status).toBe(200);
    expect(await response.json()).toEqual({ status: 'ok' });
  });
});
```

`exports.default.fetch()` goes through middleware and bindings exactly as a real
request does. (Older guides import `SELF` from `cloudflare:test`; that is
deprecated.) Hono's `app.request('/path')` is still fine for a pure routing unit
test, but it bypasses the runtime — prefer the real dispatch for anything
touching config, auth, or the database.

## LLM-indexability strategy

An agent should answer "where does X live / is there already a service for Y?"
without reading the whole tree. We get that from:

- **A README in every `src/*` folder** (from
  [`templates/folder-README.md`](./templates/folder-README.md)) listing what
  belongs there, what's inside (one line each), and where NOT to put things.
- **`CLAUDE.md` at the root** as the map + rulebook, read first by agents.
- **No barrels + filename ↔ content** — grep for a symbol lands on its definition.
- **The `@/` alias** makes import sites self-describing
  (`@/services/health-service` tells you exactly where it is).

When you add a notable service/route/utility, add a one-line entry to that
folder's README so the index stays current.
