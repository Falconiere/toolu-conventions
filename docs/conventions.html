— §00 · conventions kit

Same decisions, every new project.

This kit is a shared playbook for how we build software: what each piece of a product is for, which tools we pick once, and the rules that keep code readable for people and for AI agents.

One guide for everyone: product shape, folder trees, house rules, and how those rules are enforced — written so you can skim or dig in.

Start with why See it running Read CORE.md

— §01 · why this exists

Stop re-deciding the same questions.

Every new repo used to reopen the same debate: folder layout, naming, tests, hosting, linting, what an agent is allowed to invent. That costs time and creates drift between projects that should feel like one house.

toolu-conventions freezes those answers in markdown an AI coding agent can run. Hand it SETUP.md, answer a short intake, and the scaffold matches the last project: structure, tooling, and guard rails included. There is no CLI and no generator binary — the agent is the executor.

Root router SETUP.md → stack-agnostic CORE.md + DESIGN.md → per-stack SETUP.md, STRUCTURE.md, LIBRARIES.md, and templates/. Stacks may add rules; they must not relax a core rule.

— §02 · product shape

One product, usually three repos.

A full product is typically split so each surface can use the right defaults: a public website people can find, an app behind login, and an API both talk to. They share one design language and one set of house rules.

Public site
Marketing / content pages — fast, crawlable, static-first. Stack: marketing (Astro)
Product app
The authenticated experience — screens, forms, live data. Stack: console (React + Vite)
API
Server logic, database, auth — never ships secrets to the browser. Stack: backend-ts (Hono on Workers)

Mobile and systems work have their own kits (Expo and Rust) when the product needs them. Not every idea needs all five stacks.

— §04 · folder design

Same words, same places.

Every project is laid out so a stranger (or an agent) can guess where a screen, an API call, or a helper lives. Folders are named for jobs, not for frameworks. TypeScript stacks share one vocabulary; Rust uses the same idea with modules instead of feature folders.

TypeScript · console (canonical)

Authenticated app tree

Routes only wire URLs to screens. Product work lives under features/. Shared UI and helpers stay outside features. Imports use @/* (never deep relatives); no barrel index.ts. Canonical detail: stacks/console/STRUCTURE.md.

Rust · single crate

Modules, not a monorepo

One crate, one Cargo.toml. Each file holds one main idea. When it grows, it becomes a folder of parts — still named after that idea. Declare submodules from the parent file (src/foo.rs + src/foo/bar.rs), never mod.rs. Module tests live in a sibling tests/ folder — never in the same file as the logic. Canonical detail: stacks/rust/STRUCTURE.md.

— §05 · house rules

Rules that make code findable.

These apply to every stack. They exist so a human or an agent can open a repo cold and still know where things live, what a file is for, and whether a change is safe.

  1. 01

    One file, one job

    A file does one thing and is named after that thing. Small and clear beats a grab-bag module nobody wants to open.

    One primary named export per file. Filename ↔ export shift-card.tsx → ShiftCard. Max 300 code lines (TS) / 500 (Rust), blanks and comments excluded. No barrel index.ts re-export files (framework route entries are the only sanctioned exception).

  2. 02

    Imports point at the real file

    You always import from the file that defines something. That keeps ownership obvious and stops “junk drawer” folders from forming.

    Named exports by default. Default export only where a framework forces it (Expo Router route files; Cloudflare Worker src/index.ts). Console TanStack routes export a named Route.

  3. 03

    Tests sit next to the code

    Tests live beside the module they prove — not in a central src/tests dump. They use realistic inputs. A test that only proves a fake returns what you told it to return does not count.

    TypeScript (console, marketing, backend-ts, expo): sibling __tests__/, named after the module. Rust: sibling tests/ (same shape, different folder name) — never in the same file as the logic. Keep test trees flat. No centralized test directories under src/.

    TypeScript · colocated

    • ui/or features/…/components
      • my-component/module folder
        • my-component.tsx
        • __tests__/sibling of the module
          • my-component.test.tsx
      • button.tsxstill a single file
      • __tests__/sibling in the same dir
        • button.test.tsx

    Rust · colocated

    • project/
      • src/
        • parse_config.rs
        • tests/colocated · not __tests__
          • parse_config.rs
        • shift_store/module parts
          • query.rs
          • tests/
            • query.rs
      • tests/crate-root · integration
        • cli.rs
  4. 04

    Trust nothing at the edge

    Anything that enters the program from outside — forms, APIs, env vars, storage — is checked before use. Inside our own code, types are enough.

    Zod at every boundary; TypeScript types come from z.infer, never a parallel hand-written type. No any, no as unknown as T. Secrets never land in committed files.

    const Shift = z.object({ id: z.string(), startsAt: z.iso.datetime() });
type Shift = z.infer<typeof Shift>;
  5. 05

    Docs move with the change

    If behavior people rely on changes, the prose that describes it changes in the same commit. Modules also carry a short doc line so search and agents can orient quickly.

    Every module and public symbol gets a concise doc line /** … */ / ///. User-facing surfaces update README / guides / release notes in the same change.

  6. 06

    No debug leftovers, no silent rot

    Committed code does not leave print-debugging behind. Unused files and copy-paste clones are treated as failures, not as “cleanup later.”

    No console.log / debugger in committed TS; prefer console.warn / console.error. Gate includes knip (unused) and jscpd at threshold 0 (duplication).

— §07 · guard rails

Five layers, none optional.

Rules only matter if something enforces them. Every generated project ships five layers, ordered by how early they catch a mistake — the earliest is the cheapest. None may be disabled “just this once” to get a green build — fix the check, or change the check deliberately and say so.

  1. Rules in the repo

    A project CLAUDE.md encodes the house rules, blocked patterns, repo map, and gate commands. Agents read it first. Invisible rules do not exist.

  2. Agent hooks, while the code is written

    A committed .claude/settings.json runs agent-guardrails on every file an agent writes, and again over the whole repo before it finishes a turn. The first reports in milliseconds; the second blocks, so an agent cannot hand over red code. Agents only — which is why it replaces nothing below it.

  3. Pre-commit hooks

    Lefthook runs fast format and lint checks on staged files before the commit lands. Same idea on Rust and TypeScript stacks.

  4. One gate command

    Before every push: a single check command that type-checks, lints, formats, validates structure, hunts dead code and copy-paste, and runs tests. CI mirrors those steps by name. Structure is agent-guardrails — one config-driven module, copied into every project, enforcing what a linter cannot see: the folder tree and the shape inside each domain, READMEs, barrels, colocated tests, banned dependencies, required files, shadowing configs, committed secrets, and code patterns via ast-grep.

  5. AI code review on PRs

    Each pull request is reviewed against the repo’s own convention files from the base branch, so a PR cannot rewrite the rules it is judged by.

TypeScript stacks:

bun run check
# tsc|astro check → oxlint → oxfmt → guardrails/run.sh → knip → jscpd → tests

Rust:

cargo fmt --check && cargo clippy --all-targets -- -D warnings \
  && bash scripts/guardrails/run.sh && cargo test

Structure is machine-enforced (no axios, no barrels, kebab-case filenames, max-lines, feature isolation). This conventions repo validates its own templates via scripts/validate-templates.sh.

— §08 · how to use

Hand the kit to an agent.

Humans decide the product intent. The agent executes the scaffold. You finish the checklist only a person can complete (logins, store credentials, secrets).

  1. Create an empty project folder

    New repo or directory where the app will live.

  2. Make the kit readable

    Clone or place this kit where the coding agent can open it.

  3. Start the agent on SETUP.md

    Tell it: set up this project by following SETUP.md.

  4. Answer the intake

    Stack, project name, staging?, integrations, and (for UI stacks) a short design context.

  5. Finish the human-only checklist

    Secrets, required GitHub checks, and vendor logins the agent cannot complete for you.

When a convention changes, update the markdown and the matching templates together. Run the kit’s validation script before you distribute a change.
